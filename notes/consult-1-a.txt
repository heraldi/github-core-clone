## 1. Upload-pack v2

### Advertisement

For `GET /{owner}/{repo}.git/info/refs` with `Git-Protocol: version=2`, return:

```http
Content-Type: application/x-git-upload-pack-advertisement
Cache-Control: no-cache
```

The body is pkt-line framed. Each pkt-line begins with four ASCII hexadecimal bytes giving the total packet length, including those four bytes. The v2 advertisement is:

```text
001e# service=git-upload-pack\n
0000
0015version 2\n
0013agent=your-agent\n
0017object-format=sha1\n
0000
```

Those lengths are examples for the shown lines: `001e` is 30 bytes total for `# service=git-upload-pack\n`; `0015` is 21 for `version 2\n`; `0013` is 19 for `agent=your-agent\n`; `0017` is 23 for `object-format=sha1\n`. Omit `agent` if you do not advertise one. The object-format capability is `object-format=sha1` (or the repository’s actual format); do not advertise SHA-256 unless you implement it.

After the service preamble and its flush, v2 advertises capabilities as pkt-lines, then a flush. Common capabilities include:

```text
version 2\n
agent=<name>\n
object-format=sha1\n
ls-refs=unborn\n
fetch=shallow wait-for-done\n
```

Capability tokens and their ordering are not fixed by the protocol. Advertise only features you implement. `ls-refs=unborn` is needed if you intend to report an unborn `HEAD` as such. `fetch` may advertise the supported fetch features, commonly `shallow`, `wait-for-done`, and optionally `filter` or `ref-in-want`.

### `ls-refs` requests and responses

A v2 command request starts with the command section, followed by arguments, a delimiter packet, and command-specific pkt-lines:

```text
0014command=ls-refs\n
0001
0014peel\n
0016symrefs\n
0015ref-prefix HEAD\n
001eref-prefix refs/heads/\n
0000
```

`0001` is the delimiter packet (`0001`), not an empty pkt-line. Each `ref-prefix` is a separate argument line. Clients commonly request `peel`, `symrefs`, and one or more prefixes; some conformance checks use `ref-prefix refs/heads/`, while others request `HEAD` or additional prefixes. Do not assume a fixed order or fixed set of arguments.

A response is a sequence of pkt-lines, one per advertised ref, terminated by flush (`0000`). Each ref line is:

```text
<40-hex-object-id> SP <refname> [SP symref-target:<target>] [SP peeled:<peeled-object-id>]\n
```

Examples:

```text
003f01234567890123456789012345678901234567 refs/heads/main\n
```

The length is the number of bytes in the complete line plus four, represented as four hex digits. With `symrefs`, a symbolic `HEAD` may be:

```text
<oid> HEAD symref-target:refs/heads/main\n
```

`oid` should be the target ref’s object ID. A peeled annotated tag can be reported with an additional `peeled:<oid>` attribute.

For an unborn `HEAD`, when `ls-refs=unborn` was advertised and the client sent `unborn\n`, report:

```text
<zero-oid> HEAD symref-target:refs/heads/main unborn\n
```

Use the repository’s object-ID width (40 zeroes for SHA-1). Do not report a normal, resolvable object ID for an unborn ref.

### `fetch` request framing

A typical request has command and delimiter sections, followed by fetch arguments and a flush:

```text
0012command=fetch\n
0001
000cwant <oid>\n
000dhave <oid>\n
0009done\n
0000
```

The lengths above are illustrative: compute each from the actual ASCII bytes plus the four-byte prefix. In particular, `want` and `have` use a space before the object ID; `done` is a standalone argument line. A full clone generally has one or more `want` lines and no `have` lines.

## 2. Upload-pack v0 fallback

For `GET .../info/refs` without protocol v2 negotiation, use:

```http
Content-Type: application/x-git-upload-pack-advertisement
Cache-Control: no-cache
```

The body starts with a pkt-line service preamble, then a flush packet:

```text
001e# service=git-upload-pack\n
0000
```

The preamble is **not plain text outside pkt-line framing**. It is a pkt-line whose payload is exactly `# service=git-upload-pack\n`. For SHA-1, advertise refs as:

```text
<oid> SP <refname> NUL <capability-list> LF
```

The NUL and capabilities occur only on the first ref line. For example:

```text
<oid> HEAD\0multi_ack_detailed side-band-64k ofs-delta thin-pack
  no-progress include-tag report-status agent=forge object-format=sha1\n
<oid> refs/heads/main\n
0000
```

The wrapped capability text above is explanatory; the actual pkt-line is one line. The first advertised ref must be `HEAD` when available, so capabilities have a place to attach. If there are no refs, advertise the special zero-ID `capabilities^{}` line with capabilities, then flush; this lets the client discover capabilities in an empty repository.

For a modern clone/fetch, implement and advertise at least:

- `side-band-64k` if you will multiplex pack data and progress on fetch.
- `ofs-delta` if your pack writer can emit offset deltas; otherwise do not advertise it.
- `thin-pack` only if you support thin packs.
- `multi_ack_detailed` only if your negotiation handles it.
- `include-tag` only if you include reachable annotated tags as expected.
- `report-status` on receive-pack, not upload-pack.
- `agent=...` and `object-format=sha1` are optional metadata/capabilities; advertise the latter when supported.

A conservative server can advertise `side-band-64k` and only the negotiation/pack features it actually implements. Incorrectly advertising a capability is worse than omitting it.

## 3. Fetch response in v2

The v2 response is sectioned. A section begins with its section-name pkt-line, such as `packfile\n`; section payload follows until the next section header or the response terminator. For a simple full fetch with no haves, a minimal response is:

```text
000eacknowledgments\n
0000
0000
000dpackfile\n
... raw pack bytes ...
0000
```

`000eacknowledgments\n` is the header for the acknowledgments section. With no haves, it has no `ACK` lines; the section ends at flush. The following `0000` is the response-end packet separating that section from the next section. Then `packfile\n` introduces the pack section. The raw pack bytes are carried in pkt-lines in the packfile section; do not send an unframed HTTP body containing a bare pack after the header. Depending on negotiated features and request, sections such as `shallow-info\n` or `wanted-refs\n` may be required. Section headers are pkt-lines too.

For a depth-one request (`deepen 1`), send a `shallow-info` section before `packfile`. It contains `shallow <oid>\n` lines for commits whose parents are omitted at the shallow boundary, and optionally `unshallow <oid>\n` lines when removing existing shallow boundaries. Example:

```text
0012shallow-info\n
0033shallow <40-hex-commit-id>\n
0000
0000
000dpackfile\n
...
0000
```

The lengths shown are only correct for the corresponding exact payloads; calculate them from bytes. The `shallow` line identifies a commit boundary, not the branch tip by definition. A depth-one clone normally includes the requested tip commit and its tree/blobs, omits its parent history, and marks the tip commit shallow if it has a parent. A suite can validate this by checking the shallow-info line and by parsing the resulting pack/repository state to ensure history stops at the stated boundary. A shallow fetch of a root commit may have no boundary line because there is no parent history to omit.

For exact v2 section termination, use flush (`0000`) to end a section and response-end (`0002`) to end the response where required by the negotiated protocol. Do not treat `0002` as a flush.

## 4. Packfile parsing for receive-pack

A pack starts with 12 bytes:

```text
offset  size  contents
0       4     ASCII "PACK"
4       4     version, unsigned big-endian (commonly 2)
8       4     object count, unsigned big-endian
```

Then come `count` packed objects, followed by a 20-byte SHA-1 trailer for SHA-1 repositories. The trailer is SHA-1 over every preceding pack byte, beginning at `PACK`.

Each object begins with a variable-length header. The first byte has this layout:

```text
bits 7..4: type (4 bits)
bits 3..0: low 4 bits of uncompressed size
bit 7:     continuation flag (1 means another header byte follows)
```

Subsequent bytes contribute seven size bits each: bits 6..0 are payload, bit 7 is continuation. Accumulate the low four initial size bits and then each subsequent seven-bit group at increasing shifts. Types are 1 commit, 2 tree, 3 blob, 4 tag, 6 OFS_DELTA, 7 REF_DELTA; 0 and 5 are invalid. The size is the uncompressed size of that entry’s inflated data (delta instruction stream for delta entries).

`OBJ_OFS_DELTA` is followed by a variable-length encoded backward distance to the base object. Decode it as:

```text
distance = first_byte & 0x7f
while (first_byte & 0x80):
    first_byte = next_byte
    distance = ((distance + 1) << 7) | (first_byte & 0x7f)
base_offset = entry_offset - distance
```

This is not the same encoding as the object size varint. `OBJ_REF_DELTA` is followed by the base object’s 20-byte SHA-1, then the zlib stream. Delta entries may refer to an earlier object by offset or to an object by ID; resolve dependencies until every base is available, otherwise reject the pack.

The inflated delta data is:

```text
varint(base_size)
varint(result_size)
instructions...
```

These delta varints are little-endian base-128: seven data bits per byte, high bit means continuation. A copy instruction has opcode bit 7 set. Bits 0..3 indicate which of four offset bytes are present; bits 4..6 indicate which of three size bytes are present. Read indicated bytes in increasing little-endian byte order to form the copy offset and size. If the decoded copy size is zero, it means `0x10000`. An insert instruction has opcode 1..127 and is followed by exactly that many literal bytes. Opcode zero is invalid. Apply instructions to the base object, copying slices or appending literals, and require the final output length to equal `result_size`; also require `base_size` to equal the actual base content length.

For each reconstructed object, compute its canonical Git object ID from the reconstructed type and bytes. A delta entry inherits its type from its resolved base.

## 5. SHA-1 object storage and validation

Git object ID is:

```text
SHA1(ASCII(type) || SP || ASCII(decimal-byte-length) || NUL || content)
```

For example, a blob of three bytes `abc` hashes the bytes:

```text
blob 3\0abc
```

Use byte length, not character count. Store the uncompressed content by object ID, with its type.

Verify the pack trailer by hashing the complete pack bytes excluding the final 20-byte trailer and comparing the result to those final 20 bytes. This is separate from object-ID verification. For every non-delta object, inflate exactly the declared size, derive its type, and verify/store its canonical object ID. For delta objects, first reconstruct the full object using the delta instructions and the base object; then compute the ID from the base type and reconstructed content. The REF_DELTA base ID must resolve to an object with that ID. Also reject truncated zlib streams, invalid sizes, bad offsets, impossible deltas, duplicate or unresolved dependencies, and trailing/missing bytes inconsistent with the declared object count and trailer.

## 6. Receive-pack `report-status`

For receive-pack, the client requests report-status by advertising `report-status` in its command capabilities. The server’s unpack/status report is pkt-line framed:

```text
000eunpack ok\n
0012ok refs/heads/main\n
0030ng refs/heads/release non-fast-forward\n
0000
```

Again, the lengths are examples for the exact shown payloads: `unpack ok\n` is 10 bytes, so its pkt-line length is 14 (`000e`); `ok refs/heads/main\n` is 18 bytes, so length 22 (`0016`, not `0012`); `ng refs/heads/release non-fast-forward\n` is 39 bytes, so length 43 (`002b`, not `0030`). Calculate lengths from bytes, including the four-byte prefix. Each status payload ends in LF. The report ends with flush (`0000`).

If `side-band-64k` was negotiated for receive-pack, wrap each report pkt-line in an outer side-band packet with band byte `0x01` followed by the inner pkt-line bytes. For example, the outer payload is:

```text
0x01 || "000eunpack ok\n"
```

and its outer pkt-line length includes the outer four-byte prefix, the one band byte, and the inner pkt-line bytes. Finish the report with an outer flush packet. Do not send the inner flush as a band-1 payload in place of the outer flush.

For the two-ref case, assuming unpack succeeded, one update is fast-forward, and the other is rejected, report one line per command in the order received:

```text
unpack ok\n
ok refs/heads/main\n
ng refs/heads/release non-fast-forward\n
```

The exact ref names and order depend on the client’s commands. Only say `unpack ok` if the whole pack parsed and validated; otherwise report `unpack <error>\n` and reject the updates. A failed ref update does not by itself make unpack fail.
